## 1. 공통 정의 (C1~C3, C9가 공유)

모든 상태 판단이 같은 정의를 쓰도록 먼저 고정한다.

### 1.1 Task 분류

| 용어 | 정의 |
|---|---|
| active task | status ∈ {PENDING, ASSIGNED, IN_PROGRESS, BLOCKED} |
| terminal task | status ∈ {COMPLETED, CANCELLED} |
| **started task** | `actualStartedAt IS NOT NULL`. 현재 status와 무관하다. 한 번 시작했으면 차단·담당자 무효로 PENDING이 되어도 started다. |
| cleaning task | type ∈ {CHECKOUT_CLEANING, RE_CLEANING} |
| room workflow task | type ∈ {CHECKOUT_CLEANING, RE_CLEANING, INSPECTION, STAYOVER_CLEANING} (현재 MVP의 모든 type) |

### 1.2 "검사 대기(cleaned, awaiting inspection)" 판정 — `isAwaitingInspection(room)`

객실 enum만으로는 "청소 전 VACANT_DIRTY"와 "청소 후 VACANT_DIRTY"를 구분할 수 없다(v4 설계상 의도된 결과). 그래서 task 이력으로 판정하는 **단일 도메인 함수**를 둔다.

```text
isAwaitingInspection(room) =
  room.operationalStatus == VACANT_DIRTY
  AND C = 해당 객실에서 가장 최근의 started cleaning task 가 존재
  AND C.status == COMPLETED
  AND C를 sourceTaskId로 갖는 INSPECTION 중 InspectionRecord가 있는 것이 없음
  AND 객실에 active INSPECTION 이 없음 (있으면 "검사 대기"가 아니라 "검사 task 존재")
```

근거:
- READY에 도달하는 유일한 경로는 inspection PASSED다. 그러므로 "C 이후 검사 결과가 없다"는 조건은 "C 이후 객실이 다시 더러워질 이벤트(체크인→체크아웃)가 없었다"를 함축한다.
- 시작 전에 취소된 cleaning task는 객실에 영향이 없으므로 무시한다(`started` 기준).
- 시작 후 취소된 cleaning task가 가장 최근이면 C.status ≠ COMPLETED이므로 "검사 대기 아님"이 된다. 부분 청소를 완료로 간주하지 않는 보수적 판단이다.

이 함수는 C1(검사 작업 생성 조건)과 C9(대시보드 stage)에서 **같은 구현**을 사용한다. FE에서 다시 계산하지 않는다.

**전제:** INSPECTION의 `sourceTaskId`는 항상 그 검사가 확인하는 cleaning task를 가리킨다(자동 생성·수동 생성 모두). v4 문서에는 이 의미가 명시되어 있지 않으므로 C10에서 명시한다.

### 1.3 객실 workflow 충돌 규칙

지시서 2.2는 "객실당 IN_PROGRESS 하나"로 단순 제한하지 말고 유형별 충돌 규칙을 정의하라고 요구한다. 현재 MVP type 기준 호환성 표:

| active ↓ / 새로 생성·시작 → | CHECKOUT_CLEANING | RE_CLEANING | INSPECTION | STAYOVER_CLEANING |
|---|---|---|---|---|
| CHECKOUT_CLEANING | ✕ | ✕ | ✕ | ✕ |
| RE_CLEANING | ✕ | ✕ | ✕ | ✕ |
| INSPECTION | ✕ | ✕ | ✕ | ✕ |
| STAYOVER_CLEANING | ✕ | ✕ | ✕ | ✕ |

- 결론: **현재 4개 type은 모두 같은 "room workflow" 그룹이며, 객실당 active task는 최대 1개**다. 객실 상태(OCCUPIED vs VACANT 계열)만 봐도 turnover와 stayover는 동시에 존재할 수 없고, turnover 내부(청소→검사)는 순차적이다.
- 이 제한은 "IN_PROGRESS 하나"가 아니라 "**active(PENDING 포함) 하나**"다. PENDING 상태로 두 개가 쌓이는 것도 막는다.
- 확장성: task에 `workflowGroup` 컬럼을 두고 `UNIQUE (room_id, workflow_group) WHERE status IN (active)` partial unique index로 강제한다. 나중에 병행 가능한 type(예: 어메니티 배달, 시설 점검 task)을 추가하면 다른 group을 부여해 호환시킨다.

| 상태 | APPROVED |
|---|---|

### 1.4 Lock 순서 (교착·경쟁 방지)

room workflow를 바꾸는 모든 command는 같은 순서로 잠근다.

```text
Room (SELECT … FOR UPDATE) → Reservation → HousekeepingTask → TaskAssignment / TaskBlocker
```

- 대상 command: check-in, check-out, stayover create, task start, complete, cancel, blocker add/resolve, inspection-result, rework create, availability 변경
- Room 행 비관적 잠금으로 **같은 객실의 command를 직렬화**한다. 두 번째 요청은 첫 번째가 commit한 뒤의 최신 상태로 선행조건을 다시 평가한다. 그래서 결과는 항상 "어느 하나가 먼저 실행된 것"과 같다.
- 낙관적 잠금(`version`)은 FE가 보낸 stale version을 감지하는 용도로 함께 유지한다(409 `VERSION_CONFLICT`).
- v4 04 §4의 "version 또는 pessimistic lock을 선택"을 **room workflow command는 pessimistic, 그 외는 optimistic**으로 확정하자고 제안한다.

| 상태 | APPROVED |
|---|---|

```http

```
```json

  "kind": "CLEANING",
```

| estimatedDurationMinutes | – | 생략하면 type별 설정 기본값을 쓰고, 응답과 readiness 근거에 `durationSource=CONFIG_DEFAULT`로 표시한다 |

### 2.3 지시서 질문에 대한 답

| # | 질문 | 제안 답 | 이유 |
|---|---|---|---|
| Q1 | VACANT_DIRTY만으로 청소 생성 가능한가, 예약/체크아웃 이력도 확인하나? | **객실 상태 + active task 없음**으로 충분하다. 예약 이력은 확인하지 않는다. 대신 CHECKED_IN 예약이 그 객실에 연결되어 있으면 상태 모순으로 보고 409 `STATE_INCONSISTENT`를 반환한다. | VACANT_DIRTY는 체크아웃 외에도 검사 실패, 청소 취소, 검사 취소, 시설 복구 후 등 여러 경로로 생긴다. 체크아웃 이력을 요구하면 정작 복구가 필요한 경로가 막힌다. |
| Q2 | 청소 완료 여부는 객실 상태로만 판단하나, 선행 청소 task까지 확인하나? | **task 이력으로 판단한다**(§1.2 `isAwaitingInspection`). 객실 상태만으로는 불가능하다. | v4에서는 청소 완료 후에도 VACANT_DIRTY다. |
| Q3 | 자동 RE_CLEANING과 수동 청소는 같은 type인가? 생성 사유를 별도 저장하나? | **type은 `RE_CLEANING`을 재사용**하고, **생성 원인은 새 필드 `origin`**에 저장한다(C10). 수동 생성은 `origin=MANAGER_REWORK`이며 `reason`이 필수다. | type은 "무슨 일인가", origin은 "왜 생겼나"로 축을 분리한다. 감사 이력과 KPI(재작업률)를 origin으로 구분할 수 있다. 대안은 OPEN-2. |
| Q4 | 완료·취소된 과거 작업은 중복 제한에서 제외되나? | **제외한다.** 중복 판단은 active task만 대상이다(§1.3). | terminal task는 이력이다. |
| Q5 | 담당자·예정 시각은 필수인가? | **둘 다 선택**이다(위 표 참고). | 관리자가 상황만 기록해 두고 배정은 나중에 하는 흐름을 허용한다. |

### 2.4 생성 조건

| kind | 허용 조건 (모두 충족) | 생성 결과 | 객실 상태 |
|---|---|---|---|
| CLEANING | MANAGER · property scope · room VACANT_DIRTY · 객실에 active room workflow task 없음 · CHECKED_IN 예약 없음 | `RE_CLEANING`, origin=MANAGER_REWORK, sourceTaskId=null | 변경 없음 |
| INSPECTION | MANAGER · property scope · `isAwaitingInspection(room)` = true · active task 없음 | `INSPECTION`, origin=MANAGER_REWORK, **sourceTaskId = §1.2의 C** | 변경 없음 |

- availability(OOS 여부)는 생성 조건에 넣지 않는다. 시설 복구 전에 청소를 준비하는 흐름을 막지 않기 위해서다. OOS 중 작업 진행 정책은 v4의 OPEN을 유지한다.
- **검사만 다시 만드는 대표 케이스:** 검사 task를 시작 후 취소 → 객실 VACANT_DIRTY → C는 여전히 COMPLETED이고 검사 결과는 없음 → 재검사 생성 가능. 재청소는 필요 없다.

### 2.5 중복·재시도

| 상황 | 결과 |
|---|---|
| 같은 Idempotency-Key + 같은 payload | 최초 응답을 그대로 반환. task와 event는 추가로 생기지 않음 |
| 같은 key + 다른 payload | 409 `IDEMPOTENCY_CONFLICT` |
| 다른 key인데 이미 active task가 있음 | 409 `ACTIVE_WORKFLOW_EXISTS` + `existingTaskId`, `existingTaskType`, `existingTaskStatus` (FE가 그 task로 이동할 수 있게) |
| 동시에 두 요청 | Room lock(§1.4)으로 직렬화. 두 번째는 `ACTIVE_WORKFLOW_EXISTS`. partial unique index가 최종 방어선 |

### 2.6 이벤트

`HOUSEKEEPING_TASK_CREATED` — payload: `taskId, type, origin=MANAGER_REWORK, reason, sourceTaskId, assigneeStaffId?, durationSource`. actor=MANAGER. 자동 생성(체크아웃·검사 실패·청소 완료)은 같은 event type을 쓰고 origin만 다르다.

| 9 | task ASSIGNED, **최초 시작** (`actualStartedAt` null) | Room이 type별 시작 전 상태여야 함 → 전이 | task IN_PROGRESS, `actualStartedAt=now`, Room 전이, `TASK_STARTED` event |

| 11 | 9·10의 Room 조건 불일치 | 409 `STATE_INCONSISTENT` + ERROR 로그 (correlationId, taskId, roomId, 기대 상태·실제 상태). **임의로 보정하지 않음** | 없음 |

type별 Room 조건:

| type | 최초 시작: Room 필요 상태 → 전이 | 재시작: Room 필요 상태 |
|---|---|---|
| CHECKOUT_CLEANING / RE_CLEANING | VACANT_DIRTY → CLEANING | CLEANING |
| INSPECTION | VACANT_DIRTY + `isAwaitingInspection` → INSPECTING | INSPECTING |
| STAYOVER_CLEANING | OCCUPIED (+ 예약 CHECKED_IN) → STAYOVER_CLEANING | STAYOVER_CLEANING |

- 3번(상태 기반 멱등)과 1번(key 기반 멱등)은 둘 다 필요하다. key 없이 재전송되는 경우(예: 사용자가 새로고침 후 다시 누름)도 중복 이력을 남기지 않아야 하기 때문이다.
- 재시작 시 `actualStartedAt`은 최초 시각을 보존한다. 실제 작업 시간 분석에 필요하면 이벤트(`TASK_STARTED`, `TASK_RESUMED`, `TASK_BLOCKED`)로 구간을 재구성한다. 별도 컬럼은 추가하지 않는다.

### 3.3 동시성 케이스

| 경쟁 | 직렬화 결과 |
|---|---|
| 같은 task start × 2 | 첫 요청 성공. 두 번째는 판정 표 3번 → 200 `alreadyStarted` |
| 같은 객실의 서로 다른 task start | 정상 상태라면 §1.3 때문에 active task가 2개일 수 없다. 만약 생기면 index 위반 또는 판정 8번 → 409 |
| start ↔ blocker add | Room·Task lock으로 직렬화. blocker가 먼저면 start는 `ACTIVE_BLOCKER_EXISTS`. start가 먼저면 blocker 등록으로 BLOCKED(statusBeforeBlocked=IN_PROGRESS), Room은 진행 상태 유지 |
| start ↔ cancel | cancel이 먼저면 start는 판정 2번. start가 먼저면 cancel은 "시작 후 취소" 규칙 적용 |

## 4. C3 — 체크아웃과 stayover task (지시서 2.3)

### 4.1 판정 기준 변경 제안 (N1)

지시서 표의 `status`/`statusBeforeBlocked` 기준 대신 **`actualStartedAt` 기준**을 쓰자고 제안한다.

| stayover task | 지시서 판정 | v4.1 판정 (`actualStartedAt`) | 일치 |
|---|---|---|---|
| PENDING (한 번도 시작 안 함) | 자동 취소 | null → 자동 취소 | ✓ |
| ASSIGNED | 자동 취소 | null → 자동 취소 | ✓ |
| IN_PROGRESS | 거부 | not null → 거부 | ✓ |
| BLOCKED, before=PENDING | 자동 취소 | null → 자동 취소 | ✓ |
| BLOCKED, before=ASSIGNED | 자동 취소 | null → 자동 취소 | ✓ |
| BLOCKED, before=IN_PROGRESS | 거부 | not null → 거부 | ✓ |
| COMPLETED | 정상 | terminal → 영향 없음 | ✓ |
| CANCELLED | (표에 없음) | terminal → 영향 없음 | – |
| **PENDING/ASSIGNED인데 이전에 시작했음** (차단 해제 시 담당자 무효로 복귀, 또는 재배정) | 자동 취소 → **v4 선행조건(Room OCCUPIED)과 충돌** | not null → 거부 | 새로 커버 |

마지막 행에서 객실은 `STAYOVER_CLEANING`이다(matrix "유지"). 그래서 v4 체크아웃 선행조건 "Room OCCUPIED"를 통과할 수 없다. `actualStartedAt` 기준을 쓰면 "거부" 판정이 Room 상태와 자연스럽게 일치한다.

**일관성 확인:** "started stayover가 있으면 Room은 STAYOVER_CLEANING"이고 "unstarted만 있으면 Room은 OCCUPIED"다. 그러므로 v4의 "Room OCCUPIED" 선행조건과 v4.1의 "started stayover 있으면 거부"는 정상 데이터에서 항상 같은 결론을 낸다. 둘이 어긋나면 `STATE_INCONSISTENT`다.

### 4.2 체크아웃 transaction (v4 02 §4 Check-out 대체안)

```text
lock Room → Reservation → active stayover task (있으면)
1. Reservation CHECKED_IN, roomId 일치 확인            실패 → INVALID_STATE
2. active stayover task S 조회
   - S.actualStartedAt != null                         → 409 STAYOVER_IN_PROGRESS (전체 rollback)
3. Room OCCUPIED 확인                                  실패 → STATE_INCONSISTENT
4. S가 있으면 자동 취소:
   - S.status = CANCELLED, cancellationCode = CHECKOUT, statusBeforeBlocked = null
   - 활성 assignment 종료: unassignedAt=now, unassignedReason = TASK_CANCELLED
   - 미해결 blocker 종결: resolvedAt=now, resolutionType = TASK_CANCELLED, resolvedBy = checkout actor (삭제하지 않음)
5. Reservation CHECKED_OUT, actualCheckOutAt
6. Room VACANT_DIRTY
7. CHECKOUT_CLEANING 생성 (origin=CHECKOUT_COMMAND, unique(reservationId, type))
8. Event: [TASK_CANCELLED(S)], RESERVATION_CHECKED_OUT, ROOM_STATUS_CHANGED, HOUSEKEEPING_TASK_CREATED — 모두 같은 correlationId
9. idempotency 결과 저장 → commit
```

### 4.3 지시서 질문에 대한 답

| # | 질문 | 제안 답 |
|---|---|---|
| Q1 | BLOCKED + before=IN_PROGRESS는 항상 체크아웃을 막나? 별도 정리 명령이 필요한가? | **항상 막는다. 새 명령은 만들지 않는다.** 기존 명령으로 해결한다: ① blocker 해제 후 complete, 또는 ② MANAGER가 cancel(→ Room OCCUPIED) 후 체크아웃. FE는 거부 응답을 받으면 이 두 경로를 안내한다. 이유: 작업자가 객실 안에 있었던 작업을 자동 취소하면 작업 이력의 의미가 흐려진다. |
| Q2 | BLOCKED + before=ASSIGNED의 assignment는 자동 취소와 함께 종료되나? | **종료한다**(`unassignedReason=TASK_CANCELLED`). terminal task에 활성 assignment가 남지 않아야 한다는 v4 불변식과 일치한다. |
| Q3 | 체크아웃과 start가 동시에 오면? | Room lock(§1.4)으로 직렬화한다. **start가 먼저면** 체크아웃은 `STAYOVER_IN_PROGRESS`. **체크아웃이 먼저면** S는 CANCELLED가 되고 start는 409 `INVALID_STATE`(판정 표 2번). 어느 순서든 상태는 일관된다. |
| Q4 | 자동 취소된 task의 blocker는 이력으로 보존되나? | **보존한다.** `resolvedAt`, `resolutionType=TASK_CANCELLED`로 종결하고 삭제하지 않는다. |

### 신규 발견 N3 — 시작 후 차단된 task의 취소 권한 우회

v4는 IN_PROGRESS 취소에는 MANAGER를 요구하지만, BLOCKED 취소는 "권한 정책 충족 시"로 열려 있다. 그래서 진행 중 task에 blocker를 하나 붙이면 MANAGER 없이 취소할 수 있다.
→ **취소 권한은 `actualStartedAt` 기준으로 판정**하자고 제안한다. started task는 status와 무관하게 MANAGER + reason이 필요하다. (cancel matrix의 "시작 전/후"도 같은 기준이다.)
